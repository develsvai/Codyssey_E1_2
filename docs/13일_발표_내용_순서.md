# 1. 우리는 왜 코드를 나누는가?

### 여기서 바로 클래스부터 말하지 않는다.

아주 작은 프로그램:

```python
question = ...
answer = ...
score = ...
```

이 정도는 그냥 써도 됨.

그런데 기능이 많아지면:

```text

```

가 한 파일에 섞인다.

그러면 문제는:

> **“이 코드가 무슨 일을 담당하는지 모르겠다.”**

가 된다.

여기서 첫 번째 개념.

## 관심사

> **관심사 = 코드가 다루고 있는 문제의 종류**

예를 들어 현재 레포:

```text

```

서로 다른 관심사다.

# 2. 관심사 → 책임 → 역할

이 세 개를 여기서 명확히 고정.

### 관심사

```text
무슨 문제를 다루는가?
```

### 책임

```text
그 문제에 대해 무엇을 해야 하는가?
```

### 역할

```text
다른 객체가 나에게 무엇을 기대하는가?
```

예:

```text
Storage

관심사:
데이터 저장

책임:
파일 읽기 / 쓰기

역할:
QuizGame이 "저장해줘"라고 요청할 수 있는 대상
```

여기서 중요한 말을 하나 넣으면 좋음.

> **코드를 나눈다는 것은 파일을 나눈다는 뜻이 아니라, 책임의 경계를 나눈다는 뜻이다.**

이게 발표 전체의 핵심 중 하나.

# 3. 그러면 객체란 무엇인가?

> **객체는 프로그램 안에서 어떤 상태와 행동을 하나의 대상으로 묶어서 다루는 단위다.**

```python
quiz = Quiz(
```

가 있고,

```text
행동

to_dict()
```

가 있다.

그래서:

```text
Quiz 객체

상태
├─ question
├─ choices
└─ answer

행동
├─ display()
├─ is_correct()
└─ to_dict()
```

라고 보여주면 된다.

# 8. 이제 코드가 실제로 어떻게 실행되는가?

여기에서 **런타임**을 먼저 정의.

이걸 안 하면 C/JVM/Python 설명에서 다시 꼬임.

## 런타임이란?

쉽게:

> **작성된 프로그램이 실제로 실행되고 있는 시간과, 그 실행을 가능하게 만드는 환경을 런타임이라고 부른다.**

조금 더 구체적으로:

```text
프로그램 실행
│
├─ 메모리 사용
├─ 함수 호출
├─ 객체 생성
├─ 라이브러리 사용
├─ 오류 처리
└─ 메모리 정리
```

이런 것들이 실제로 일어나는 영역.

여기서 중요한 것:

```text
C에도 런타임이 있다.
Java에도 있다.
Python에도 있다.
```

다만 **언어마다 런타임을 구성하는 방식이 다르다.**

# 9. 먼저 C

여기서는 C를 **절차지향 언어라고 단정하기보다**, 실행 모델을 보여주는 게 핵심.

```text
hello.c
   ↓
전처리
   ↓
컴파일
   ↓
어셈블
   ↓
hello.o
   ↓
링커
   ↓
실행 파일
   ↓
OS가 로드
   ↓
CPU 실행
```

### `.o`란?

> 아직 완성된 프로그램은 아니지만 기계어가 포함된 목적 파일.

예를 들어:

```text
main.o
math.o
print.o
```

를 링커가 연결해서:

```text
program
```

으로 만든다.

### 링커

> 따로 컴파일된 코드와 라이브러리를 서로 연결해서 최종 프로그램을 만든다.

여기서 너무 깊은 ELF/심볼 테이블까지 가지 않는다.

# 10. Java

이제 비교.

```text
Main.java
   ↓
javac
   ↓
Main.class
   ↓
Bytecode
   ↓
JVM
   ↓
Interpreter / JIT
   ↓
CPU
```

여기서 중요한 포인트:

> Java 컴파일러가 처음부터 특정 CPU용 기계어 실행파일을 만드는 구조는 아니다.

먼저:

```text
JVM이 이해할 수 있는 bytecode
```

를 만든다.

그리고 JVM이 실행한다.

---

## JVM

> Java 프로그램이 실행될 수 있도록 제공되는 가상 실행 환경.

여기서:

```text
객체 메모리
메서드 실행
GC
스레드
클래스 로딩
```

등을 관리한다.

---

# 11. JIT는 왜 나오나?

JVM이 계속 bytecode만 하나씩 해석하면 느릴 수 있음.

그래서:

```text
이 코드 엄청 자주 실행되는데?
```

싶은 부분을:

```text
Bytecode
 ↓
JIT
 ↓
현재 CPU용 native machine code
```

로 바꿔서 다시 사용.

즉:

> **자주 쓰는 코드는 실행 중 컴파일해서 빠르게 돌리자.**

정도로.

# 12. 그다음 Python

이제 Python이 나온다.

CPython 기준으로 설명한다고 반드시 말해.

```text
hello.py
   ↓
Python parser/compiler
   ↓
code object / bytecode
   ↓
CPython interpreter
   ↓
실행
```

그래서:

> **Python은 컴파일을 아예 하지 않는다**

가 아님.

CPython도 소스를 내부 bytecode 형태로 바꾸는 과정이 있다.

차이는:

```text
C
→ 주로 실행 전에 native machine code 생성

Java
→ bytecode → JVM → 필요하면 JIT

CPython
→ Python bytecode → CPython interpreter 실행
```

이라는 것.

이 표 하나로 정리하면 좋다.

|          | C             | Java         | CPython                    |
| -------- | ------------- | ------------ | -------------------------- |
| 중간 결과    | 목적 코드         | JVM bytecode | Python bytecode            |
| 주요 실행 주체 | CPU           | JVM          | CPython                    |
| JIT      | 일반적인 기본 모델 아님 | 핵심 최적화       | 기본 CPython은 일반적 JIT 모델과 다름 |
| 런타임 관리   | 비교적 직접적       | JVM 적극 개입    | Python runtime 적극 개입       |

# 16. 메모리 관리와 GC

이제 실행 모델을 설명했으니 GC가 들어가도 안 뜬금없음.

## CPython

먼저:

```text
reference counting
```

객체를 몇 군데에서 참조하고 있는지 관리.

```text
참조 2
 ↓
참조 1
 ↓
참조 0

→ 객체 정리 가능
```

그런데:

```text
A → B
↑   ↓
└───┘
```

같은 순환 참조가 존재할 수 있음.

그래서:

```text
reference counting
+
cyclic GC
```

가 사용된다.

---

# 17. Java GC

Java에서는 개발자가:

```c
free(ptr)
```

처럼 직접 객체 메모리를 해제하지 않는다.

JVM이:

> **“이 객체에 앞으로 도달할 수 있는가?”**

를 기준으로 판단하고 필요 없는 객체를 회수한다.

그래서 크게:

```text
CPython
→ reference count 중심 + cycle GC

Java
→ JVM GC의 reachability 기반 관리
```

정도로 비교.

GC 알고리즘 세대별 세부 구현까지 들어가면 발표가 터질 수 있으니 여기까지.

```text
짧고 표현력 높은 코드
빠른 개발
큰 라이브러리 생태계
```

---

# 19. 발표의 최종 결론

여기서 다시 객체지향으로 돌아오면 발표가 닫힌다.

처음:

```text
우리는 왜 코드를 나누는가?
```

에서 출발했음.

결국:

```text
문제를 어떻게 바라볼 것인가
        ↓
관심사를 어떻게 나눌 것인가
        ↓
각 부분에 어떤 책임을 줄 것인가
        ↓
객체와 클래스로 어떻게 표현할 것인가
        ↓
그 코드를 각 언어의 실행 환경이 어떻게 실행할 것인가
```

라는 이야기였던 것.

마지막 문장은 이런 식이면 좋겠어.

> **C, Java, Python은 서로 다른 선택을 한 언어입니다. 하지만 어떤 언어를 사용하든 프로그램의 관심사를 어디에서 나누고, 각 부분에 어떤 책임을 줄지는 결국 개발자가 판단해야 합니다. 클래스는 그 판단을 표현하는 도구 중 하나일 뿐입니다.**

---

# 이번 발표에서는 과감하게 뺄 것

범위 관리 때문에 이건 본문에서는 안 하는 걸 권함.

* 동기/비동기 상세
* 멀티스레드 / 멀티프로세스
* SOLID 전체
* 디자인 패턴
* Java GC 알고리즘 종류
* CPython GIL
* Python 내부 캐시 상세
* ELF / PE 구조
* JVM class loader 세부 구조
* PyInstaller
* “왜 Python은 엔터프라이즈가 아닌가” 논쟁

질문 나오면:

> “그 내용은 지금 설명한 실행 모델에서 한 단계 더 내려가야 하는 내용이라 오늘은 범위에서 제외하겠습니다.”

라고 잘라.

**강연에서는 모든 질문에 끝까지 답하는 게 좋은 발표가 아니야. 발표의 논리 흐름을 지키는 것도 발표자의 역할**이니까.

---

## 전체 흐름을 한 장으로 만들면

```text
[왜 코드를 나누는가?]
          ↓
[관심사 / 책임 / 역할]
          ↓
[객체]
          ↓
[클래스]
          ↓
[Quiz / Storage / QuizGame]
          ↓
[객체 간 의존성]
          ↓
────────────────────
      설계 영역
────────────────────
          ↓
[런타임이란?]
          ↓
 ┌────────┼────────┐
 ↓        ↓        ↓
 C       Java    Python
 ↓        ↓        ↓
Native   JVM     CPython
         ↓        ↓
        JIT      Bytecode
          ↓
[메모리 / 객체 / GC]
          ↓
────────────────────
[언어는 도구이고
 설계의 경계는 개발자가 정한다]
```

이 정도면 **하루짜리 심화 발표 범위로도 꽤 많아.** 더 넣기보다 각 구간 사이의 연결 문장을 제대로 만드는 쪽이 훨씬 효과적일 거야. 특히 이번에는 `관심사 → 객체 → 클래스 → 실제 레포 → 런타임 → 언어별 실행` 순서만 안 무너지게 잡아도 첫 발표에서 겪었던 “뒤에서 설명할 내용이 앞에서 먼저 질문으로 튀어나오는 문제”가 많이 줄어들 거야.
